**A change a person can see is verified by driving the running app in a browser before it is
reported done.** Not by reading the diff, not by reasoning about the JSX, and not by the test
suite: the Vitest environment dev-env ships is `node`, with no DOM, so **no test in this repository
renders a component**. A green run is evidence about server code and nothing else. The failure
this rule exists for is specific and common — a change breaks the render, every test still passes,
and the work is reported as done.

This is not an argument for a DOM test environment. Rendering tests have their own costs; for an
app like this one, driving the real thing is cheaper and more honest.

## How to drive it

1. Make sure the dev server is running (`dev-environment` explains the container and the
   per-worktree ports; the published app port is the `appOffset` entry in
   `.devcontainer/docker-compose.worktree.yml`, and Conductor's Run menu opens it).
2. Open the affected page with the browser automation available to you (Claude in Chrome, a
   Playwright script, or a screenshot tool), take the action, and look at the result. A
   screenshot in the report is worth more than a paragraph.
3. Check the states that are easy to forget: **empty, loading, error, and long content**. A
   component that only ever renders its happy path in your check is half verified.
4. Check every variant the repository has: both locales, both themes, mobile width, and — for a
   tenant-scoped app — a second tenant.
5. For an email template, open it in the react-email preview (`pnpm dev:email`) rather than
   sending it; the preview renders the same component the send path does.

## What to say afterwards

Report what you actually did. "Tests pass" and "I loaded `/settings` at mobile width and the
header renders correctly" are different claims, and only the second is about the UI. If you could
not run the app, say the change is **unverified** rather than letting a green suite imply
otherwise. Name the page, the action, and what you saw.
