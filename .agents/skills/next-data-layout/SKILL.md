Companion skills: `next-caching` (cache directives, tags, invalidation) and
`next-server-actions` (mutations, forms, validation). This skill is the structural layer
underneath both — start here when scaffolding a route or domain.

## Two layers

- **`/app/<route>/` route sidecars** — files private to one route: `page.tsx`,
  `layout.tsx`, `loading.tsx`, `data.ts`, `actions.ts`, `validations.ts`, `api/route.ts`.
  Default home for anything only this route uses.
- **`/lib/<domain>/` shared primitives** — files owned by a domain, used by any number of
  routes (and by webhooks, cron jobs, scripts): `cache.ts`, `data.ts`, `service.ts`, plus
  domain-named pure-logic files.

Start in `/app/<route>/`. Promote to `/lib/<domain>/` when a trigger below fires.
Cross-route sharing happens through `/lib`, never by importing across `/app` siblings.

Paths are logical. With a `src/` directory, read `/app` and `/lib` as `src/app` and
`src/lib`; in a monorepo, `/lib/<domain>/` may itself be a shared package.

## Where does this code go

| You are writing…                                              | It goes in…                                                  |
| ------------------------------------------------------------- | ------------------------------------------------------------ |
| A read for one page/route                                     | `./data.ts` (route sidecar)                                  |
| A read shared by 2+ routes, or by a webhook/cron/script       | `/lib/<domain>/data.ts`                                      |
| A mutation (Server Action)                                    | `./actions.ts` — never `/lib`; see `next-server-actions`     |
| Write-path business logic (the actual DB write / rules)       | `/lib/<domain>/service.ts`                                   |
| An input schema                                               | `./validations.ts`                                           |
| A client-refetch HTTP endpoint (only if actually refetched)   | `./api/route.ts`                                             |
| A cache tag touched outside its route                         | `/lib/<domain>/cache.ts` — see `next-caching`                |
| A cache tag used only inside one route                        | `./data.ts`                                                  |
| Branching/edge-case domain logic (calc, parse, state machine) | `/lib/<domain>/<operation>.ts`                               |
| An auth / session check                                       | Entry points only (`page.tsx`, `api/route.ts`, `actions.ts`) |
| A pure formatter/helper used only here                        | Inline or `./` — don't promote                               |

## Route sidecars — `/app/<route>/`

- **`page.tsx`** — Server Component. Auth/authorization for the route, imports queries
  from `./data.ts`, renders.
- **`layout.tsx`** — Standard layout. Server Component unless interactivity is required.
- **`loading.tsx`** — Suspense fallback for the route; required whenever `page.tsx` awaits
  runtime data (`next-caching` covers exactly when).
- **`data.ts`** — Pure read queries scoped to this route. Take tenant keys (e.g. `orgId`)
  as parameters and filter by them. Owns route-private cache tags; imports shared tags
  from `@/lib/<domain>/cache`.
- **`actions.ts`** — All Server Actions for this route; `next-server-actions` owns the
  contract for what belongs in here.
- **`validations.ts`** — All input schemas for this route. Neutral file (no `"use
server"`, no `"use client"`). Imported by `actions.ts` server-side and by client
  components for form validation.
- **`api/route.ts`** — HTTP wrapper around `data.ts` for client-side refetch. Auth, then
  call `data.ts`, then `Response.json`. Lives in a child `api/` subfolder because
  `route.ts` cannot coexist with `page.tsx` at one segment. Exists only when a client
  component actually refetches.

## Shared primitives — `/lib/<domain>/`

Baseline layout — prescribed names, all standard:

```
/lib/<domain>/
├── cache.ts         (shared TAGS constants — builders, sentinels)
├── data.ts          (pure shared queries — no auth, take tenant keys)
├── service.ts       (write-path business logic called by /app actions.ts)
├── validations.ts   (optional — shared schemas)
├── types.ts         (optional — shared types)
└── *.test.ts        (co-located tests)
```

Beyond the baseline, name files for the operation they perform — `calculator.ts`,
`parser.ts`, `state-machine.ts`, `shipping-calculator.ts` — each with a sibling
`*.test.ts`.

- **`data.ts`** — takes tenant keys, filters by them, owns its `cacheTag()`s. May
  intentionally skip caching when atomic semantics need a fresh row. No `auth()` inside.
- **`service.ts`** — the default home for write-path business logic. Auth-free; assumes
  the caller (a route action, webhook, or cron) already authorized the operation, and
  takes the resolved actor/tenant as parameters. Testable without route plumbing.
- **Pure-logic files** — no I/O. Plain data in, plain data out — exhaustively testable.
- **`cache.ts`** — the single source of truth for shared tags; see `next-caching`.

Mutations are not promoted to `/lib`: Server Actions stay in `/app/<route>/actions.ts` so
the `"use server"` boundary and auth check stay adjacent (Rule 16 — full contract in
`next-server-actions`); `service.ts` exposes the operation the action calls after auth +
validation.

## When to promote to `/lib/<domain>/`

1. **Shared cache tags** — a tag invalidated from more than one place (sibling route,
   webhook, cron). → `cache.ts`.
2. **Shared queries** — the same read needed by 2+ routes or a non-route caller. →
   `data.ts`.
3. **Non-trivial domain logic** — branching, edge cases, or invariants worth testing.
   Promote even if only one route uses it today. → a domain-named file.
4. **Write-path business logic** — the operation behind a mutation, and any
   transactional/cross-domain flow. → `service.ts`.

Keep in `/app/<route>/`: a one-line formatter used only here; a query shaped for exactly
this view (route-specific `include`/`select`); a schema for a form that exists only on
this route.

**Extract, don't copy.** Before modeling a new file on an existing one, grep for how many
places already declare that same type or helper. Zero or one existing copy: modeling on it
is fine. Two or more: the deliverable is the extraction plus the new caller, not a third
copy — and a brief that says "mirror the reference file's shape verbatim" is an
instruction to copy-paste, so rephrase it as "extract the shared shape, then import it".
Extract the invariant (the type, the validation rule, the step sequence); leave the
caller-specific literals at the call site. Say in the PR what was duplicated and where it
now lives, so the refactor reads as the fix it is rather than scope creep.

## Directory layout

A domain with a shared layer and one consuming admin route:

```
/lib/discounts/                    ← shared primitives for the discounts domain
├── cache.ts                       (DISCOUNT_TAGS — used by /app and webhooks)
├── data.ts                        (getDiscountCodeByCode — used by checkout)
├── service.ts                     (createDiscountCode — owns the write)
├── calculator.ts                  (pure discount math — domain-named)
└── calculator.test.ts

/app/system/discount-codes/        ← admin route that manages the domain
├── page.tsx                       → GET /system/discount-codes (HTML)
├── loading.tsx                    (required — page awaits searchParams)
├── data.ts                        (getDiscountCodes — admin listing)
├── actions.ts                     (thin: auth + validate + service + invalidate)
├── validations.ts                 (form input schemas)
├── discount-code-form.tsx         (route-private client component)
├── [id]/page.tsx
└── new/page.tsx
```

`data.ts` imports `DISCOUNT_TAGS` from `@/lib/discounts/cache` for `cacheTag()`;
`actions.ts` imports it for `updateTag()`. A checkout route elsewhere imports
`getDiscountCodeByCode` and `calculateDiscount` from `/lib/discounts/` — without ever
reaching into `/app/system/discount-codes/`. The full worked version of every file in
this example is in `references/templates.md`.

## Rules

1. **Reads only live in `data.ts`** — the route's `./data.ts` or shared
   `/lib/<domain>/data.ts`. `page.tsx` and `api/route.ts` import from one of those. Not:
   querying directly in `page.tsx`; not: reads inside `actions.ts`.
2. **`data.ts` is pure** in both layers — no `auth()`, no session lookups, no
   session-derived state. Take tenant keys as parameters and filter by them. Not: a
   function that takes a tenant key but doesn't `where` on it.
3. **Every query exports its return type** —
   `export type FooData = Awaited<ReturnType<typeof getFoo>>` — so client consumers stay
   type-safe. Use the ORM's generated types for parameters/intermediates, but keep the
   exported consumer type inferred so it tracks `include`/`select`/transform changes. Not:
   a hand-written return type that drifts.
4. **Input schemas live in `validations.ts`**, not `actions.ts` or `data.ts`. Use the
   project's validation library; export both the schema and its inferred type. Not:
   schemas inline in `actions.ts` or duplicated across server and client.
5. **`data.ts` (both layers) and `service.ts` start with `import "server-only"`.** Keeps
   server code from leaking into a client bundle (type-only imports from client
   components stay legal). Queries feeding client components `select` only what the
   view needs — never pass full rows with sensitive fields across the RSC boundary.
6. **`/lib` never imports from `/app`.** `/lib` is the lower layer. If something in
   `/lib` seems to need `/app`, it belongs in `/lib` too.
7. **Routes don't cross-import sibling routes.** `/app/checkout/...` must not import
   `/app/system/discount-codes/data.ts` — that's the promotion trigger: hoist the shared
   piece into `/lib/<domain>/`.
8. **Server Actions stay in `/app/<route>/actions.ts`, never `/lib`** — full contract in
   `next-server-actions`.

## Rationale (one line each)

- **Why `data.ts`** — the same query runs during SSR (`page.tsx`) and during client
  refresh (`api/route.ts` + a fetcher). One source of truth prevents drift.
- **Tenant scoping ≠ authorization** — `data.ts` still takes `orgId` and filters every
  query by it; that's scoping. "Does this actor have access to this `orgId`?" is the
  entry-point auth check.

## When to ask the user

This skill prescribes structure and data flow, not library choices.

- **An existing route uses a different pattern** (inline fetch in `page.tsx`, no
  `data.ts`) — in an interactive run, ask whether to refactor it or match it.
- **Component placement is unclear** — co-locate a route-private component or put it in a
  shared folder; ask when it's not obvious which.

Precedence with existing code: for a small edit to a route that already violates the
pattern, match local style; for a new route or domain, apply this pattern; for larger
cleanups, propose the refactor rather than performing it silently.

Non-interactive fallback: match whatever the lockfile shows for each library; don't
introduce a new dependency.
