## The devcontainer

This repository is mounted at `/workspace` inside the container — not at
`/workspaces/<name>`, which is the devcontainer CLI's own default and the path a stale
`.mcp.json` still names.

- Start it with `devcontainer up --workspace-folder .`. Use
  `devcontainer up --workspace-folder . --remove-existing-container` whenever anything under
  `.devcontainer/` changed: a plain `up` runs `docker compose up -d --no-recreate`, which reuses a
  container built from the old definition.
- Run everything else through `devcontainer exec --workspace-folder . <command>`,
  except inside `mobile/` — that project runs on the host, not the container (`mobile-boundary`). Never drive the
  services with raw `docker compose` — the compose project name, the per-worktree override file and
  the mounts all come from the devcontainer CLI, and a hand-run `docker compose up` creates a second
  set of containers that fight the first for ports.
- The `app` service runs with `network_mode: service:db`, so it has no network namespace of its
  own: **every host port is published on the `db` service**, not on `app`. A port added to `app` in
  the override file publishes nothing.

## Ports are per worktree

`.devcontainer/initialize.sh` generates `.devcontainer/docker-compose.worktree.yml` on every start.
It derives a host port base from `DEV_ENV_PORT`, then `CONDUCTOR_PORT`, then a hash of the workspace
path, and publishes every port at a fixed offset from it — so several worktrees of this repository
run at once. Inside the container the app still listens on the port compose injects as `PORT`, with
3000 published as a fallback. Set `DEV_ENV_PORT` to pin a base; never hand-edit the
override file, and never pin a port in a script (see `toolchain`).

Two failures come from this, and both name themselves:

- **`initialize: port base N is unavailable`** — another compose project already publishes a port in
  this range. Stop it or set `DEV_ENV_PORT`. Ignoring it is worse than it looks: Docker rolls the
  network endpoint back when it cannot publish, leaving a container running with no interfaces, which
  surfaces later as `EAI_AGAIN` on every registry request rather than as a port error.
- **`initialize: this workspace's container was created before the current port list`** — Docker
  fixes port bindings at container creation, so an existing container keeps the old ones while the
  override file claims the new ones. The override reads correct and the port answers nothing.
  Recreate with `--remove-existing-container`.

## The pre-commit hook in a linked worktree

`lint-staged` stashes unstaged changes so only the staged half of a partially staged file is
formatted, and that stash backup fails in a linked worktree ("cannot save the current index state").
The symptom is every commit rejected with nothing wrong in the diff. Run `pnpm format:write` over the
changed files yourself, then commit with `--no-verify`. Never disable the hook repo-wide, and never
skip the formatting step — `--no-verify` is only safe _because_ you already formatted.
