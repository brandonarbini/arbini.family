## The token is required everywhere; only its value changes

Production carries a real provider key. Every other environment — the devcontainer, a Cursor
cloud VM, CI, a preview deploy — carries a **sandbox** key: Postmark's sandbox server, a
provider test key, whatever accepts messages, shows them in the provider's activity UI, and
delivers nothing. Declare the token as required in `lib/env/server.ts`, with no `.optional()`
and no environment conditional:

```ts
POSTMARK_API_TOKEN: z.string().min(1), // sandbox key outside production; never optional
```

This is strictly better than the two shapes it replaces:

- **A live token in development** really mails your users, from anyone's local run, from any
  seeded fixture.
- **An optional token with a graceful no-op** is the trap. A blank value in production turns
  every send into a silent skip; the warning is one log line nobody greps, the delivery row says
  `skipped` and looks deliberate, and weeks pass. Making the parse fail on a blank means a
  deploy that cannot send mail does not deploy.

With a sandbox key every environment exercises the whole path — render, API call, the returned
message id, the delivery row — and you can read the actual email in the provider's UI. The
sandbox key lives with the other development secrets (`env-and-secrets` says where).

## The From address is a constant in code

It must match a sender signature or domain verified with the provider, so it is not a value an
operator can usefully change per environment — a wrong value is a hard provider rejection at send
time. Put it in the module next to the senders, not in env:

```ts
const FROM_ADDRESS = "noreply@example.com"; // must match a verified sender signature
```

## Render HTML and plaintext from one template, and test the render

Every send provides both parts; a missing plaintext part costs deliverability and breaks clients
that prefer it. Render both from the same component so they cannot drift.

Emails are the one UI nobody looks at after shipping, which makes them the right place for a
cheap render test: assert the subject, the key link, and that the plaintext part is non-empty. A
template that throws on a null field is otherwise discovered by a user.

`pnpm dev:email` runs the react-email preview so a template can be read in a browser without a
send; `verify-in-browser` says to look at it before reporting a template change done.

## Record every send

One row per intended send, with the provider's message id and a terminal status (`sent`,
`failed`). It turns "did they get the invitation" from a support guess into a query, and it is the
row an at-most-once claim in a background job keys on. If a `skipped`
status exists at all, audit every path that writes it against the no-op trap above.

## Rationale

- **Why not a queue in front of the provider** — providers already accept-and-retry, and the job
  runner already gives durable retries for the surrounding step. A bespoke outbox adds a second
  at-least-once layer to reconcile.
- **Why the delivery row is not just logging** — logs expire and are not queryable per recipient.
  The row is product data: it answers a user's question, and it deduplicates.
