Ships with the parallel test-database harness: one migrated template database, a
private clone per test worker, and a global `afterEach` that truncates every table.
Read the harness setup for the mechanism. What follows is only what that mechanism
makes true, because it inverts the habits of manual-cleanup test suites.

## Consequences (this is the whole point)

These follow from the architecture and contradict manual-cleanup habits:

- **Write NO cleanup code.** No `deleteMany`/`DELETE FROM` in `afterEach` or `afterAll`,
  no arrays of created IDs, no manual rollback, no "reset" helper. The infrastructure
  owns this. Cleanup code in a test is a bug report about a misunderstanding.
- **Never issue a raw `BEGIN` from a test.** On a pooled client it checks out an
  arbitrary connection and leaves a transaction open on it; the pool leaks a connection
  per occurrence and eventually deadlocks the suite. If you need transactional behavior,
  call the ORM's transaction API from the code under test.
- **Never create rows in `beforeAll`** that later tests depend on. The truncate after the
  first test wipes them and every subsequent test fails with a missing row. Use
  `beforeEach` — the clone is empty and the inserts are cheap.
- **Never use `test.concurrent` / `describe.concurrent` in a DB-touching file.**
  Concurrency between _files_ is safe (separate databases); concurrency _within_ a file
  is not, because those tests share one database and one test's truncate wipes another's
  rows mid-flight. Keep DB tests sequential.
- **Code under test may freely commit.** Real transactions, `createMany`, bulk updates,
  triggers — all expected, all wiped. Do not contort production code to be
  rollback-friendly for tests.
- **The nuance:** a mid-test delete is fine when it _arranges_ the scenario — e.g.
  deleting rows to construct an empty-table state the function must handle. That is
  setup, not cleanup. The distinction is whether it runs before the assertion (arrange)
  or after it (cleanup, forbidden).
