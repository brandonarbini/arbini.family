`mobile/` is not a directory of this project. It is a **separate project that happens to live in
this tree**: its own `package.json`, its own lockfile, its own `node_modules`, its own toolchain,
its own CI job. This skill is about the boundary — what the root must do, and must not do, about
it. Everything about working inside it is in `mobile/AGENTS.md` and the skills nested beside it;
read those before changing anything down there.

## It runs on the host

The repository's rule is that every package, build, test and lint command goes through
`devcontainer exec --workspace-folder .`. **`mobile/` is the exception**, and it is not a
preference: Metro, Xcode, the iOS Simulator and the Android emulator only run on macOS, and the
container publishes no port Metro could bind. So mobile commands run from a host shell:

```sh
cd mobile
pnpm install
pnpm start        # Metro
pnpm ios          # Metro + iOS Simulator
pnpm lint
```

Put `cd <absolute path>/mobile &&` in front of every mobile command, even when you believe the
shell is already there. A shell keeps whatever directory the last `cd` left it in, and one
root-directory command in between is enough to make the next `pnpm ios` run the **root** package.

## Never run `pnpm install` at the repository root from the host

The container bind-mounts this working tree, so the container and the host share one root
`node_modules`. A host install re-resolves every platform-specific package for macOS and replaces
the container's Linux binaries with Mach-O ones, which breaks `next dev`,
`prisma` and `vitest` until a container-side install puts them back:

```sh
devcontainer exec --workspace-folder . pnpm install --frozen-lockfile
```

That is also what `mobile/pnpm-workspace.yaml` exists to prevent. It declares `packages: []` — an
**empty workspace root**, which stops pnpm walking up out of the directory and finding the
repository's workspace. Do not delete it, and do not reach for `--ignore-workspace`: that flag
holds only as long as every person and every tool remembers it (third-party tooling never will),
and it tells pnpm to ignore the whole file, `allowBuilds` included, so the install then fails on an
unapproved build script.

For the same reason, `mobile` is not a member of the root `pnpm-workspace.yaml`. Two lockfiles is
the design, not an oversight.

## The root toolchain skips it

Each exclusion exists because the two projects have different toolchains, not because mobile code
is exempt from quality gates — it runs its own lint, typecheck and format from its own install,
under its own CI workflow.

| Where               | What                                                                                                 |
| ------------------- | ---------------------------------------------------------------------------------------------------- |
| `tsconfig.json`     | `exclude` lists `mobile` — it is typechecked against its own tsconfig and its own React Native types |
| `eslint.config.mjs` | ignores `mobile/**` — `lint` is `eslint .`, and the web config has no resolver for that tree         |
| `.prettierignore`   | ignores `/mobile` — it formats itself, and two formatters over one tree undo each other              |
| `vitest.project.ts` | excludes `mobile/**` — **not** `vitest.config.ts`, which dev-env owns and rewrites on every apply    |

That last one has already gone wrong once: the exclusion was written into the owned
`vitest.config.ts` and disappeared on the next apply. `vitest.project.ts` is the project's own file
and is merged into the owned config — arrays concatenate, so an `exclude` there adds to the owned
one rather than replacing it.

## Nothing is imported across the boundary

The app talks to this repository over **HTTP**, the same way any other client would. There is no
import path from `mobile/` into the root, and none from the root into `mobile/`.

If the two must agree on a shape — a response body, an enum, a route's parameters — the honest
options are a generated client, a published package, or a type-only import behind an alias that is
_only ever_ `import type`. A value import pulls the web app's dependency tree into the React Native
bundle, and the failure surfaces at Metro bundle time in a file nobody edited.

## What this skill is not

It is the web↔mobile boundary and nothing else. React Native, Expo, Metro, EAS, navigation,
styling, the SDK version this app is pinned to — all of that is `mobile/AGENTS.md`, the skills
nested under `mobile/`, and Expo's own versioned documentation. An agent working inside `mobile/`
should be reading those, not this.

`repo-layout` states the three kinds of "skill" that can exist in this tree — this project's own,
and `mobile/.agents/skills/`, the mobile project's
own — so they don't get confused with each other.

## Contract

These must be true of this repository. Audit each bullet by reading the repo — no command here
checks them.

- `mobile/pnpm-workspace.yaml` exists and declares no members — `packages: []`, or no `packages` key at all. — An empty workspace root is a wall rather than a rule: pnpm stops walking up the moment it finds the file, so a command run from inside the directory cannot reach the repository's install. Without it, `expo lint` — which shells out to an install as its dependency check — re-resolves the whole repository for macOS and replaces the container's Linux binaries. `--ignore-workspace` is not the alternative: it holds only as long as every tool remembers the flag, and it tells pnpm to ignore this file's `allowBuilds` too.
- The root `pnpm-workspace.yaml` does not list `mobile`. — The two lockfiles are the point, not an oversight: the app installs on the host for Metro and Xcode, while the repository installs inside the container for Linux, and one shared install cannot be both. Adding it as a member makes every container-side install re-resolve the React Native tree as well.
- The root `tsconfig.json` excludes `mobile`. — The app is typechecked against its own tsconfig, its own React Native types and its own installed SDK. Left in the root program, `pnpm typecheck` compiles those files against the web app's lib and JSX settings and reports errors nobody can fix from here.
- The flat ESLint config ignores `mobile` — an `ignores` entry of `mobile`, `mobile/` or `mobile/**`. — `lint` is `eslint .`, so without the ignore the root config lints React Native source with the web app's plugins — rules it has no resolver for, against an install that is not there. The app runs its own `expo lint` from its own config.
- `.prettierignore` ignores `mobile`. — The app formats itself from its own install, with its own Prettier version and its own config. Two formatters over one tree means each reformats what the other wrote, and the CI format gate fails on files this repository's toolchain never wrote.
- `vitest.project.ts` excludes `mobile/**`. — The suite is pinned to `environment: "node"` and a real Postgres, so a React Native test picked up by it fails on an import it cannot resolve. The exclusion has to live in `vitest.project.ts` and not in `vitest.config.ts`: dev-env owns the latter and rewrites it on every apply — which is how one repository lost this exclusion already — while arrays in the project file are merged into the owned config rather than replacing it.
- `mobile/AGENTS.md` exists and `mobile/CLAUDE.md` contains a line that is exactly `@AGENTS.md`. — An agent working inside the app should be handed that project's own rules rather than the repository root's, which are about a container it must not use and a database it cannot reach. Nested instruction files are how every tool discovers those, and the import keeps one file authoritative instead of two copies drifting apart — the same arrangement the root uses.
- If `mobile/.agents/skills` exists, `mobile/.claude/skills` is a symlink to `../.agents/skills`. — The app's own skills belong beside the app, where a directory-scoped listing offers them to an agent standing in `mobile/` and to nobody else. Claude Code finds them through `.claude/skills` while every other tool reads `.agents/skills`, so the symlink is what keeps one copy — exactly as at the repository root, which dev-env owns and this one the project does.
