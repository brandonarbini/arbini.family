## Which env files are tracked

Git ignores `.env*.local` and `.env.*`, then negates two of them. Both tracked files are
documentation or harness config, never secrets:

- `.env.example` — tracked. The list of variables the app needs, with placeholder values.
- `.env.test` — tracked. Points the suite at the test database; see `prisma-harness`.
- Bare `.env` matches neither pattern and stays tracked. It carries the development defaults every
  bootstrap reads — devcontainer, Cursor VM, CI — so a rule that swallows it leaves a fresh checkout
  with no baseline environment at all. Nothing secret belongs in it, and the same goes for
  `.devcontainer/.env`.
- `.env.local`, `.env.production`, `.env.development.local` are ignored, and so are `.context/` and
  `.devcontainer/docker-compose.worktree.yml` — per-checkout scratch that would otherwise follow one
  machine's port allocation into everyone else's checkout.

The negations depend on file order: `!.env.example` only works below the `.env.*` rule it negates.
Verify the policy with `git check-ignore -v <file>`, not by reading the lines.

## Reading a variable

Every read goes through `lib/env/server.ts` (server and Node bootstrap) or `lib/env/client.ts`
(`NEXT_PUBLIC_*` only, safe in a Client Component). Both parse their zod schema once at import, so a
missing required variable fails loudly at boot instead of surfacing as `undefined` three layers
later.

**Adding a variable means editing the schema, not the call site.** Add it to the right module, add a
placeholder to `.env.example`, then import it. A `NEXT_PUBLIC_*` value belongs only in the client
module — Next inlines those at build time, and they must be read as static members for that to work.
Everything else is server-only and must never be imported into a Client Component.

Ownership splits down the middle:

- **dev-env owns** `lib/env/parse.ts` and `eslint.dev-env.mjs`, rewritten on every apply.
- **The project owns** `lib/env/server.ts`, `lib/env/client.ts` and `.env.example`. dev-env
  scaffolds each once when absent and never touches it again — the variable list is project
  knowledge, and migrating existing reads behind the gate is the project's own work.

zod 4 is required: the scaffolded schemas use v4 APIs and do not compile on an older major.

## The gate, and the one way around it

`eslint.dev-env.mjs` restricts `process.env` through `no-restricted-properties` (not the deprecated
`no-process-env` — this one also catches `process.env["X"]` and destructuring, and names the module
to import instead). The project's flat config imports it and spreads `...devEnvEslint` as the **last
element** of the exported array. Later entries win in flat config, so a spread placed anywhere but
last can be switched back off by a project-owned block below it — silently.

The only sanctioned exemption is `lint_ignores` under `[env]` in dev-env's own
`projects/arbini.family.toml`. The standard already exempts `lib/env/**`, `instrumentation.ts`,
tests, and the harness dev-env generates. An inline `eslint-disable` instead of a registry entry
hides the exemption from the fleet, so use the registry.

`next.config.ts` must import `./lib/env/server`, and must be `.ts` rather than `.mjs`/`.js` — a
native `import()` of a JavaScript config cannot resolve the TypeScript module at all. That one import
is the whole guarantee: it makes `next build` fail up front on a missing variable, instead of one
page render failing deep into the build.

## Where a secret actually lives

Never in the repository. Per environment:

- **Devcontainer** — gitignored `.devcontainer/.env.local` (and `.env.local` at the root for app
  values), loaded by Compose `env_file`.
- **CI** — GitHub Actions secrets, referenced from `.github/workflows/ci.yml`.
- **Vercel** — project environment variables, set in the dashboard.

`pnpm env:cloud` prints the block a cloud environment still needs: the committed root `.env` is
excluded because the checkout already carries it, gitignored files are included, and the variables that do
not belong on a cloud VM are held back with the reason printed to stderr — the app's own origin variable, which the cloud
bootstrap pins itself; every `*DATABASE*URL*` / `*POSTGRES*URL*`, since the VM has its own
PostgreSQL; and
`VERCEL_*` / `TURBO_*` / `NX_*` build metadata that a `vercel env pull` drags in. Stdout is the block
and notes go to stderr, so `pnpm --silent env:cloud | pbcopy` copies only what is pasteable.
