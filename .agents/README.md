# .agents

Tool-neutral home for agent instructions in this repository.

- **[`AGENTS.md`](../AGENTS.md)** (repo root, the standard location) holds only what
  every change needs: how to run commands, the project's own always-needed context, the
  handful of rules that are not enforced by lint, and the index of skills below.
- **`skills/<name>/SKILL.md`** holds everything needed only sometimes. Skills are loaded
  on demand, so they cost nothing until they are relevant.

## Pointing a tool at these skills

`.claude/skills` is a symlink to `.agents/skills`, so Claude Code discovers them with no
extra configuration. Other tools should either be pointed at `.agents/skills` directly
or given their own symlink:

```sh
ln -s ../.agents/skills .<tool>/skills
```

Discovery is one level deep — `skills/<name>/SKILL.md` — so this directory stays flat.

A checkout with `core.symlinks=false` (some Windows and CI environments) materializes
the symlink as a text file. If a tool reports the skills as missing there, read
`.agents/skills` directly instead.

## Where a skill lives

Skills nest at **project boundaries**, never at directory boundaries inside one project. A nested
project — its own `package.json`, its own lockfile, its own `AGENTS.md`, such as `mobile/` in a
repository that also has a web app — gets its own `skills/` directory, because an agent standing
in it should not be handed the other project's skills. A plain directory of the same project does
not: its skill is needed by _callers_ elsewhere in the tree (a caller reaching for a shared helper,
a route reaching into a domain folder), and a skill nested inside the directory the caller never
opens would simply never load.

## What belongs where

Sorted by where the knowledge belongs, not by how important it is:

|                       | Test                                                                 |
| --------------------- | -------------------------------------------------------------------- |
| `AGENTS.md`           | Repo-specific **and** needed on nearly every change                  |
| A repo-specific skill | Repo-specific **and** needed only sometimes                          |
| A portable skill      | **Not repo-specific** — true across projects, whatever the frequency |

If a rule would read identically in an unrelated codebase, it is portable, even if it is
critical. If lint can state it, it belongs in the lint config and in no prose at all.

Portable skills are staged here for promotion to dev-env — not to a user-level skills
directory — which folds a proven skill into the shared template set it applies across
every managed repository. Each opens with a marker line saying so, and that line is also
the test: a portable skill that cannot honestly carry it has repo detail in it and needs
splitting.

## Skills owned by dev-env

A `SKILL.md` whose body begins with the line `<!-- Generated by dev-env -->` is owned by
dev-env: a standard writes it, and it is rewritten byte-for-byte on every `dev-env apply`.
Treat it like generated code. Extend it by adding a **sibling** skill under `skills/`,
never by editing the generated file directly — a hand-edit is drift, and the next apply
silently overwrites it. A `SKILL.md` without that marker line is this repository's own;
edit it freely.

## Writing a skill

The `description` in the frontmatter is the only thing a model sees until the skill
loads, so it must say **when to load me**, not **what I am about**. List concrete
triggers: paths and globs, verbs, symptoms, library names, and the phrasings someone
would actually type. A description that reads as a summary never fires — that is why the
eight subagents this directory replaced went unused.

In the body: no persona preamble (a skill instructs the agent already in the seat); point
at existing rationale docs (a subsystem's own `README.md`, a `product/` directory, and
the like) rather than restating them, since those are the rationale layer and a copy will
drift; lead with what is non-obvious; use real paths and symbol names.
