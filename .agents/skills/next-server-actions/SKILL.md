## Rules

3. **Every entry point does its own auth check before calling `data.ts` or mutating.**
   `page.tsx`, `api/route.ts`, and `actions.ts` each verify the session and confirm access
   to the resource. Not: skipping auth and relying on the data layer to gate access. Auth
   library is project-specific.
4. **`api/route.ts` is a thin wrapper** — auth, call `data.ts`, `Response.json`. In a
   child `api/` subfolder (or descriptive sibling like `orders-feed/`). Not: business
   logic or transformation in the handler; not: `route.ts` at the same segment as
   `page.tsx` (they collide on GET and the build fails).
5. **Only create `api/route.ts` when a client component actually refetches.** Not:
   speculatively exposing every query as HTTP.
6. **Server Actions stay in `/app/<route>/actions.ts`; write logic lives in
   `service.ts`.** Don't put `"use server"` in `/lib`. The action does auth + validate +
   invalidate; `/lib/<domain>/service.ts` (auth-free, resolved actor/tenant params) owns
   the actual write. Only a genuinely trivial single ORM call may inline in the action,
   and even then prefer the service so the domain owns its writes. Not: `service.ts` (or
   any `/lib` function) calling `auth()` or reading the session.

## The action contract (Rules 7 and 10, the action half)

Rule 10: `actions.ts` contains only `"use server"` mutations — no reads, no helpers.

Rule 7: every Server Action validates input through a `validations.ts` schema before
anything else — with `safeParse`, returning a typed result object, never throwing a
validation error to the client (a thrown error is an opaque prod `digest` with no field
feedback):

1. Auth first.
2. `safeParse` the input. On failure, **return** a typed error result — don't throw.
3. Call the `/lib/<domain>/service.ts` function that owns the write (`next-data-layout`).
4. Invalidate tags with `updateTag()` (`next-caching`).
5. Return a typed success result.

```ts
"use server";

export type ActionState =
  | { ok: true; id: string }
  | { ok: false; fieldErrors: Record<string, string[]>; formError?: string }
  | null;

export async function createDiscountCodeAction(
  _prev: ActionState,
  formData: FormData,
): Promise<ActionState> {
  const session = await requireSystemAdminForAction();

  const parsed = createDiscountCodeSchema.safeParse({
    code: formData.get("code"),
    organizationId: formData.get("organizationId"),
    // ...coerce the rest of the fields...
  });
  if (!parsed.success) {
    return { ok: false, fieldErrors: parsed.error.flatten().fieldErrors };
  }

  const code = await createDiscountCodeSvc(session.user.id, parsed.data);
  updateTag(DISCOUNT_TAGS.discountCodes(parsed.data.organizationId));
  return { ok: true, id: code.id };
}
```

The `(prevState, formData)` signature is what `useActionState` expects. If the action
instead takes a typed object (called imperatively, e.g. from `react-hook-form`), keep the
same return-a-result-object discipline — just parse the object instead of a `FormData`.

## `redirect()` throws — don't wrap it

`redirect()` and `notFound()` signal by throwing a special control-flow error that
Next.js catches. Never call them inside a `try/catch` that swallows the error, and never
wrap them in your own error handling. Call `redirect()` after the successful write,
outside any try/catch — return-based error handling only guards the validation/business
path above it.

## Default form — `useActionState` + native `<form action>`

```tsx
"use client";
import { useActionState } from "react";
import { createDiscountCodeAction, type ActionState } from "./actions";

export function NewDiscountCodeForm() {
  const [state, formAction, pending] = useActionState<ActionState, FormData>(
    createDiscountCodeAction,
    null,
  );

  return (
    <form action={formAction}>
      <input name="code" />
      {state?.ok === false && state.fieldErrors.code?.[0] && (
        <p role="alert">{state.fieldErrors.code[0]}</p>
      )}
      {/* ...remaining fields... */}
      <button disabled={pending}>Create</button>
    </form>
  );
}
```

`pending` drives the disabled/loading state; for a submit button in a child component,
`useFormStatus()` reads the same pending state without prop-drilling. Field errors come
straight off the returned `state`.

## When `react-hook-form` is warranted

Reach for `react-hook-form` (with the same schema from `validations.ts` via
`zodResolver`, or the project's equivalent) only when the form has real client-side
complexity: many fields, cross-field validation, dynamic field arrays, per-keystroke
validation, or wizard steps. It calls the action imperatively rather than through `<form
action>`:

```tsx
"use client";
import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import {
  createDiscountCodeSchema,
  type CreateDiscountCodeInput,
} from "./validations";
import { createDiscountCode } from "./actions";

export function NewDiscountCodeForm() {
  const form = useForm<CreateDiscountCodeInput>({
    resolver: zodResolver(createDiscountCodeSchema),
  });

  const onSubmit = form.handleSubmit(async (input) => {
    const result = await createDiscountCode(input);
    if (!result.ok) {
      for (const [field, msgs] of Object.entries(result.fieldErrors)) {
        form.setError(field as keyof CreateDiscountCodeInput, {
          message: msgs[0],
        });
      }
    }
  });
  // ...
}
```

The schema still lives in `validations.ts` so client and server validate identically. The
action still returns a typed result — the client maps its `fieldErrors` back onto the
form.

## `useOptimistic` (brief)

For a mutation whose result the user should see instantly (toggling a flag, adding a list
item), wrap the displayed state in `useOptimistic` so the UI updates before the action
resolves, then reconciles when the server responds. It complements the pattern above — the
action still validates, calls the service, and invalidates tags; `useOptimistic` only
affects the client-side render while the action is in flight.

## Rationale

- **Why not Server Actions for reads** — actions POST (no GET/HTTP-cache semantics) and
  dispatch **sequentially**, so using them as read fetchers serializes concurrent reads.
  GET handlers keep HTTP semantics and can call the same cached `data.ts` functions
  server-side.
- **Why `validations.ts`** — a neutral file lets `actions.ts` (server) and client form
  resolvers share one schema. `"use server"` in `actions.ts` creates import friction for
  client components; `data.ts` conflates reads with input shapes.
