`package.json` and `pnpm-workspace.yaml` belong to this project: dev-env states what must be true of
them and reports drift, but never edits them. The `## Contract` below is the authoritative list; this
body is the reasoning behind the parts that are not obvious.

## Versions are pinned in three places that must agree

`packageManager` is what Corepack resolves pnpm from, `engines.node` is what makes an install on the
wrong Node major fail loudly, and `.node-version` (dev-env-owned) is what the container and any
version manager read. Node 24 and pnpm 11.17.0 are the fleet values; the
devcontainer inherits them from its base image and a Cursor VM installs them, so a local edit to one
of the three only produces two machines that disagree about one lockfile.

To change any dependency version: edit `package.json`, run
`devcontainer exec --workspace-folder . pnpm install`, and commit the lockfile with the change.
Never run the install on the host, and never hand-edit `pnpm-lock.yaml`.

## `dev` is composed, its leaves are not

Start everything with `pnpm dev`. That script is not owned key by key — it is composed from
the `dev:*` leaves this selection implies, because what belongs in it is only knowable once every
standard is resolved. The contract states the exact string.

**No leaf pins a port.** The devcontainer injects `PORT`, and a number written into a script
overrides it and binds a port the compose override publishes neither as `APP_PORT` nor as the
3000 fallback — reachable from nowhere. `dev-environment` covers the port math.

- `dev:web` — the app server, bare.
- `dev:email` — the react-email preview, fixed on container port 3001 because
  react-email's own default is 3000, which the app already holds. It is deliberately
  **not** a member of `dev`: it is an authoring tool with its own Run entry, not something the app
  needs to run. `@react-email/ui` must be declared even though nothing imports it — react-email 6
  ships the preview server there and, when it is missing, the CLI _prompts_ to install it; under a
  Run entry nobody can answer, so the terminal hangs and no port is ever bound.

A superseded leaf left behind (`dev:next`, `email:dev`) is a second entry point to one server that no standard owns and nothing keeps
in step. Delete it rather than keeping the two in sync by hand.

## `allowBuilds` is a consequence of the selection

pnpm 11 will not finish an install while a dependency carries a build script no `allowBuilds` entry
decides on: it exits non-zero with `ERR_PNPM_IGNORED_BUILDS` rather than skipping the script
silently, so one missing entry breaks every install in the repository. The decisions this selection
implies, all in `pnpm-workspace.yaml`:

- `prisma`, `@prisma/engines`: **true** — the query engines are the build; skipped, `prisma generate`
  has nothing to emit.
- `esbuild`: **true** — Vitest transforms through it, and its install script fetches the platform
  binary.
- `unrs-resolver`: **false** — reached through `eslint-config-next`; it publishes a prebuilt binary
  per platform, so building from source only redoes what the package ships.
- `@tailwindcss/oxide`: **true**, on Tailwind v4 only. Keyed on the dependency rather than the
  framework, since no standard implies Tailwind and a v3 project would get an inert entry.

Anything else a project installs is the project's own decision, and its own decision always wins:
these are the entries the selection requires, not the whole file. Two neighbours matter as much —
`confirmModulesPurge: false`, without which pnpm stops for an interactive confirmation that a
container bootstrap or a CI job can never answer; and the migration off the older spellings, since
pnpm 11 reads build decisions only from `allowBuilds`. A `pnpm` key in `package.json`, or
`onlyBuiltDependencies`/`ignoredBuiltDependencies` anywhere, is inert: the repo looks configured
while the install still stops.

## Lint, format, and editor wiring

- Flat config only — `eslint.config.mjs` (or `.js`/`.ts`). ESLint 9 ignores `.eslintrc*` entirely, so
  a rule added to one never runs and the file only misleads. Delete it.
  `lint` is `eslint .` over the whole repository: `next lint` was removed in Next 16 and only ever
  covered the app directory.
- `.prettierignore` lists `pnpm-lock.yaml`. pnpm owns that file's formatting, and reformatting it
  invites merge conflicts while turning the format gate red on a file nobody edits by hand.
- `vitest` stays on the pinned major. `vitest.config.ts` is dev-env-owned and rewritten on every
  apply — it wires the per-worker database harness, and the harness is
  written against one major (v4 moved the global-setup context type), so an older major receives
  owned files that do not compile.
  What only this project knows about its suite — a directory whose tests belong to another toolchain,
  a timeout, an extra alias — goes in `vitest.project.ts`, scaffolded once and merged into the owned
  config (arrays concatenate), never into the owned file itself.
- `.vscode/settings.json` points `typescript.tsdk` at `node_modules/typescript/lib`, so the editor
  and `pnpm typecheck` cannot disagree about a version this repo pins.
- `.mcp.json`, if present, must name `/workspace` — the mount this repo actually has. A server
  configured for the older `/workspaces/<name>` starts in a directory that does not exist.

## Contract

These must be true of this repository. `pnpm dev-env status` reports each one that is not.

- package.json sets `packageManager` to `pnpm@11.17.0`. — Corepack resolves the pnpm the container and CI both run from this field, so a stale or missing pin is how two machines end up on two pnpm majors against one lockfile.
- package.json sets `engines.node` to `>=24 <25`. — The container, CI and .node-version all run one Node major; the range is what makes an install on a different one fail loudly instead of at run time.
- pnpm-workspace.yaml sets `confirmModulesPurge: false`. — pnpm otherwise stops for an interactive confirmation when it has to purge node_modules, which in a container bootstrap or a CI job is a hang nobody can answer.
- pnpm settings live in pnpm-workspace.yaml: no `pnpm` key in package.json, and no `onlyBuiltDependencies` / `ignoredBuiltDependencies` keys anywhere. — pnpm 11 reads build decisions from `allowBuilds` in pnpm-workspace.yaml; the older spellings are inert, so a repo carrying them looks configured while the install still stops on ERR_PNPM_IGNORED_BUILDS.
- pnpm-workspace.yaml `allowBuilds` records a decision for every package the selected standards install with a build script. — pnpm 11 exits non-zero with ERR_PNPM_IGNORED_BUILDS rather than silently skipping an undecided build script, so one missing entry fails every install in the repository.
- `.vscode/settings.json` sets `typescript.tsdk` to `node_modules/typescript/lib` and `typescript.enablePromptUseWorkspaceTsdk` to true. — Without it the editor type-checks with its own bundled TypeScript, so what a contributor sees and what `pnpm typecheck` reports can disagree on a version the repository pins.
- `.mcp.json`, if it exists, names no `/workspaces/` path. — The devcontainer mounts this repository at `/workspace`; a server configured for the older `/workspaces/<name>` path starts in a directory that does not exist.
- `dev:web` is exactly `next dev`, with no port. — The devcontainer injects PORT and `next dev` honours it, so the one number that is right here is the one this repo already computed; a pinned port overrides that env var and binds a port the compose override publishes neither as APP_PORT nor as the 3000 fallback.
- `start` is exactly `next start`, with no port. — `next start` reads PORT the same way `next dev` does, and drifts the same way when pinned.
- There is no `dev:next` script. — `dev:web` is the canonical leaf name the composed `dev` script and the Conductor run entries use; a surviving `dev:next` is a second way to start the one server that nobody owns and nothing keeps in step.
- `lint` runs ESLint over the whole repository — `eslint .`. — `next lint` was removed in Next 16 and only ever covered the app directory; the flat config is what decides scope now.
- `typecheck`, `format` and `format:write` scripts exist. — CI and the converge workflow invoke them by name; a repo that spells one differently silently skips that gate.
- The Next toolchain is declared: typescript, eslint, prettier, eslint-config-next, eslint-plugin-jsx-a11y and eslint-config-prettier. — The recommended flat config imports all three ESLint packages; a missing one is a config that throws on load rather than a rule that quietly does not run.
- A flat ESLint config exists (one of eslint.config.js, eslint.config.mjs, eslint.config.cjs, eslint.config.ts). — ESLint 9 reads only the flat config; without one `eslint .` lints with its built-in defaults and reports nothing the project cares about.
- No legacy `.eslintrc*` file remains. — They are inert under ESLint 9's flat config and only mislead: a rule someone adds there never runs.
- `dev` is exactly `pnpm dev:web` — composed from the `dev:*` leaves the selection implies, with no port in it. — What belongs in `dev` is the set of long-running leaves the selection implies, which is knowable only once every standard is resolved; the email preview is deliberately not a member, since it is an authoring tool with its own run entry rather than something the app needs in order to run.
- `test` runs `pnpm test:env vitest` and `test:run` runs `pnpm test:env vitest run` (trailing flags are the project's own). — The database harness reads .env.test, so both entry points go through the `test:env` wrapper; a bare `vitest` runs the suite against the development database.
- `vitest` is declared at `^4.0.8`. — The generated harness is written against one vitest major — v4 moved the global setup context type and v3 differs again — so a project left on an older major gets owned files that do not compile.
- prettier, husky and lint-staged are declared. — Two layers on purpose: the hook fixes staged files locally and is fast, but it is bypassable and only exists on machines that ran an install, while CI is the gate that actually blocks a merge.
- `format` and `format:write` scripts exist. — CI runs `pnpm format` as its gate; the write half is what a contributor runs to satisfy it.
- `prepare` is `husky`. — husky v9 installs the hooks directory from `prepare`, which pnpm runs after every install; without it the pre-commit hook exists in the repo but is never wired into .git.
- package.json `lint-staged["*"]` is `prettier --ignore-unknown --write`. — `*` with --ignore-unknown covers ts/tsx/md/json/yml without a glob list that drifts from what Prettier actually handles.
- `.prettierignore` lists `pnpm-lock.yaml`. — pnpm owns the lockfile's formatting; reformatting it invites merge conflicts for no gain, and the format gate would fail on a file nobody edits by hand.
- `react-email` is a dependency at `~6.9.0`. — react-email 6 consolidated the component exports v4 split across @react-email/components and @react-email/render, so a major move is a template rewrite and has to be deliberate rather than an install-date accident.
- `@react-email/ui` is a devDependency at `~6.9.0`. — Nothing in project source imports it, which is exactly why it has to be declared: react-email 6 ships the preview server separately and, when it is absent, the CLI _prompts_ to install it — under a Run entry there is nobody to answer, so the terminal sits on a hidden y/n forever and no port is ever bound.
- `dev:email` is exactly `email dev --dir emails --port 3001`. — The preview's container port and the compose publish have to agree on one number; leaving the pin to the project is what let one repo ship a bare `email dev` whose run entry opened a port nothing was listening on.
- There is no `email:dev` script. — Left behind it is a second entry point to the same server that no standard owns and nothing keeps in step.
