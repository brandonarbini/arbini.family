## Prefer `vi.fn()` + `vi.mocked()` over a `vi.hoisted` state box

Two shapes show up for mocking a module's dependencies. The second is common in older test files
in this fleet; do not copy it into a new one.

**Preferred:** mock the module with `vi.fn()` for each function, then configure and assert per
test:

```ts
vi.mock("./client", () => ({ fetchThing: vi.fn() }));
import { fetchThing } from "./client";

it("returns the fetched value", async () => {
  vi.mocked(fetchThing).mockResolvedValue({ id: "1" });
  const result = await underTest();
  expect(fetchThing).toHaveBeenCalledWith("1");
  expect(result).toEqual({ id: "1" });
});
```

**Avoid for new tests:** a `vi.hoisted` box that a mock factory closes over and every test mutates
directly:

```ts
const { state } = vi.hoisted(() => ({
  state: { fetchResult: null as unknown },
}));
vi.mock("./client", () => ({ fetchThing: () => state.fetchResult }));
```

`vi.hoisted` exists to dodge a temporal-dead-zone error caused by `vi.mock` factories being hoisted
above imports — a workaround for module load order, not a mocking primitive. Using it as a shared
mutable box means every test in the file reads and writes the same object, so a test can pass or
fail depending on what an earlier test left behind, and the box hand-rolls call capture that
`vi.fn()` already gives for free via `.mock.calls` and `toHaveBeenCalledWith`. Reach for
`vi.hoisted` only for its actual purpose — lifting a genuinely hoisting-order-sensitive value
above the mock call — never as a place to store mutable test state.

## App-wide setup mocks vs per-file mocks

`vitest.setup.ts` is for mocks every test needs regardless of what it is testing — typically
neutralizing a framework marker (a `server-only` import guard) so modules load at all under the
test environment. Put a mock there only when nearly every test file would otherwise repeat it
verbatim. Everything that varies by what the test exercises — the specific functions a unit
calls, their return values, their call assertions — belongs in that file's own `vi.mock(...)`
calls. A global mock returning file-specific data is invisible coupling: a reader has to go find
the setup file to understand what a call actually returns.

## Resetting mocks between tests

Decide per mock, not by reflex:

- `vi.clearAllMocks()` (or `.mockClear()`) wipes call history but keeps configured
  implementations — use when tests share a `mockResolvedValue` set up once in `beforeEach` and
  only need clean call assertions.
- `vi.resetAllMocks()` (or `.mockReset()`) also clears implementations, snapping every `vi.fn()`
  back to `undefined` — use when tests configure behaviour individually and a leftover
  implementation from a previous test would be a correctness bug, not just assertion noise.

Run whichever is chosen in `beforeEach`, not by hand at the top of each test — the point is that a
new test cannot inherit a previous test's mock state by accident, which is exactly the failure
mode `vi.hoisted` boxes are prone to.

## When not to mock

If a dependency is the database or the ORM client, do not mock it to make a test faster or more
isolated — `db-test-isolation` explains the per-worker, truncated database that makes testing
against the real thing both fast and safe. Mocking the ORM just moves the bug from "slow test" to
"test that passes against a query that does not actually work."
