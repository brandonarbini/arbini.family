A rename is the one schema change that can destroy production data while every test passes. Four
things make it safe, and all four are easy to skip.

## Hand-write the migration

`prisma migrate dev` does not detect renames. It renders one as `DROP` plus `CREATE`, which is
correct for the schema and catastrophic for the rows — every tenant's content in that table is
gone. Generate nothing; write the `ALTER ... RENAME` statements by hand and leave the schema change
in the same commit.

Never hand-edit a migration that has already been applied anywhere. A correction is a new
migration.

## Wrap the file in an explicit transaction

Prisma does **not** wrap a migration file in a transaction. A file that fails on statement nine of
twenty leaves the database half-renamed, with no recorded failure to roll back from and no way back
except a hand-written inverse.

```sql
BEGIN;

ALTER TABLE proposals RENAME TO suggestions;
ALTER TABLE suggestions RENAME COLUMN proposer_id TO suggester_id;
-- every constraint, every index, every enum, in one unit

COMMIT;
```

Not: relying on the migration runner to make the file atomic. Not: splitting one rename across two
migration files, which reintroduces the same partial state between them.

## Put a preflight query in the header, with its expected row count

Every `RENAME` hard-codes an identifier that must already exist. Constraint and index names drift —
a manual hotfix, an older Prisma version, a restored backup — and a drifted name fails the
migration mid-file. Catch it before the deploy, not during it.

```sql
-- Preflight — run against production first. Expect exactly 15 rows
-- (the pkey appears twice, as a constraint and as an index):
--   SELECT conname FROM pg_constraint WHERE conrelid = 'proposals'::regclass
--   UNION ALL
--   SELECT indexname FROM pg_indexes WHERE tablename = 'proposals';
```

State the number. "Run this and eyeball it" is not a check; a count is.

## Sweep the strings the database already holds

A schema rename almost never finishes at the schema. Audit and event tables store the old spelling
as data, and `RENAME` does not touch data. Go looking for:

- `action`, `event`, `kind` and `target_type` columns holding a dotted or snake-cased name
- tool, job, queue and function name columns
- keys **inside** JSON/JSONB columns, not just their values
- keys inside cached or denormalized aggregate documents

Put that sweep in its own migration, make it **idempotent** — rewrite only rows still in the old
shape, so re-running it is a no-op — and add a test that replays it against old-shape rows rather
than asserting on a freshly-seeded database:

```ts
// lib/<domain>/rename-persisted-strings.db.test.ts
// Insert rows in the pre-migration shape, run the migration's statements, assert the new
// shape. A test built from current fixtures cannot fail, because current fixtures are
// already correct.
```

## The deploy window is the part that bites

When the build command is `prisma migrate deploy && build`, the migration runs against production
**before** the new build is promoted. For the whole build-and-promote window the _previous_
deployment is still serving traffic: old code, querying the old table name if it still exists, and
writing rows in the old shape. Those writes land **after** the sweep already ran, so the sweep
misses them.

Two consequences:

1. Re-run the sweep's statements once after promotion. This is why idempotency is a requirement
   and not a nicety.
2. If ORM model or field names moved, migration and code must ship together — the old client
   queries a table that no longer exists the moment the migration commits, so that window is an
   outage, not a degradation. Either accept it knowingly on a low-traffic deploy, or do the rename
   in the expand/contract shape (add the new name, dual-write, backfill, switch reads, drop the
   old) instead of in place.

## Rationale

- **Why not expand/contract every time** — it is three deploys and a dual-write path for a change
  that an in-place rename does in one. For a product where a minute of 500s on one deploy is
  acceptable, in-place is the cheaper correct answer; the point is to choose it deliberately
  rather than discover the window afterwards.
- **Why the sweep gets its own migration** — it is the one part that may need re-running, and a
  migration runner will not re-run a file it has recorded. Keeping it separate makes "run these
  statements again" a copy-paste rather than a surgery.
