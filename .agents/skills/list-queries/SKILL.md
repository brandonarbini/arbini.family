Design every list, picker and search surface for the row count the table will actually reach —
tens of thousands of rows per tenant, not the dozen in the seed. Retrofitting this after a table
grows means rewriting the UI contract (page numbers, full-list props) as well as the query, so get
the shape right the first time.

## The rule

**Never load a whole table to search or pick from it.** Concretely:

- No `<select>`, combobox or dropdown populated by fetching every row. A picker over an
  unbounded table searches server-side as the user types and returns a small capped set.
- No fetch-all-then-filter, in memory or in the client. `.filter`/`.find` over a query result is
  a smell that the criterion should have been a `WHERE` clause.
- No offset pagination (`?page=3`, `skip: (page - 1) * pageSize`) on a table that can grow past
  a few thousand rows: the database still walks every skipped row, and a concurrent insert shifts
  rows between pages. Use **keyset (cursor) pagination**: order by a stable unique tuple, take
  `limit + 1`, and use the extra row as the "there is more" signal rather than a `COUNT(*)`.

## Shape of a list query

```ts
async function listThings(input: {
  tenantId: string;
  query?: string;
  cursor?: string;
  limit?: number;
}) {
  const limit = Math.min(Math.max(input.limit ?? 50, 1), 100); // capped, never unbounded
  const items = await prisma.thing.findMany({
    where: {
      tenantId: input.tenantId, // scope at the query, over an indexed column
      ...(input.query
        ? { name: { contains: input.query, mode: "insensitive" } }
        : {}),
    },
    orderBy: [{ createdAt: "asc" }, { id: "asc" }], // stable tiebreaker
    take: limit + 1,
    ...(input.cursor ? { cursor: { id: input.cursor }, skip: 1 } : {}),
  });
  const hasMore = items.length > limit;
  const page = hasMore ? items.slice(0, limit) : items;
  return { items: page, nextCursor: hasMore ? page[page.length - 1].id : null };
}
```

- `limit` is always clamped server-side regardless of what the caller asks for — an unbounded
  `limit` is the same bug as no pagination.
- The `where` scopes by the tenant or owner id first, over a composite index that leads with it.
  A full scan that happens to be correct is still a full scan.
- Every list function takes a free-text `query`, matched case-insensitively across the natural
  keys a human would say (name, email, reference number), so a caller can find a row instead of
  paging to it. This is the single highest-leverage item here, for people and for agents alike.

## Search-as-you-type pickers

A command-palette-style picker is a small, separate concern from the list page: a route that
takes a short free-text query and returns a tightly capped, ranked set for a dropdown — not a
paginated browse.

- Return an empty result immediately for a blank query rather than running one that matches
  everything.
- Debounce on the client (150–250 ms) and cancel the in-flight request with an `AbortController`
  when a keystroke supersedes it, so slow responses cannot land out of order.
- Cap hard (`take: 10`). If one request searches several kinds of record, cap **each group**
  independently so a noisy group cannot crowd out another.
- Scope and index exactly as any other list query; a typeahead is not exempt from tenant scoping
  because its result set is small.
