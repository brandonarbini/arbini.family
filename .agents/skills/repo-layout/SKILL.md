## One package, at the root

This repository is a single package whose root is the app's root, with no workspace member
holding a second app tree. There is no `src/` or `apps/web` — the app lives
directly at the root.

That is not a style preference. Everything the toolchain generates resolves from the root,
including the Vitest config, the Prisma harness and `test/db.ts`, `lib/env/*`,
the container and Conductor scripts, and the `@` alias they all import through.
Moving the app down a level points every one of them at a directory with no app in it, and
splits what is one Vercel project into two.

When something genuinely is a separate project — its own toolchain, its own install, as `mobile/` is —
it nests with its own workspace root instead of becoming a member of this one.

## The prescribed structure

Each root directory is one capability. `app/` holds only the HTTP adapter for the capabilities that
need one; anything not in this table is this project's own and should be rare. **Load** names the
skill that governs each directory once a file lands there — this skill only answers which top-level
directory a file belongs in.

| Root dir                       | What it is                                                                                | Load                                                                           |
| ------------------------------ | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `app/`                         | Next.js routes and their sidecars — `page.tsx`, `data.ts`, `actions.ts`, `api/route.ts`   | `next-data-layout`, `next-caching`, `next-server-actions`, `verify-in-browser` |
| `components/`, `hooks/`        | UI shared across routes                                                                   | —                                                                              |

| `package.json`, config         | scripts, versions, env files, the devcontainer                                            | `toolchain`, `env-and-secrets`, `dev-environment`                              |

Dependency direction runs one way: code in `app/` imports
from `lib/`, and `lib/` never imports back. If something in `lib/` seems to need `app/`,
it belongs in `lib/` too.

## `lib/` is grouped by domain, not by layer

Group by what the code is about — `lib/billing/`, `lib/auth/`, `lib/inventory/` — with one concept
per kebab-case file, named for the thing it is: `lib/billing/proration.ts`, `lib/auth/session.ts`.

Do not create `lib/utils/`, `lib/helpers/`, `lib/common/` or a root `shared/`. Each is a directory
whose name says only that nobody decided where the file went, and each grows without limit because
nothing is ever out of scope for it. (`lib/utils.ts` holding the single shadcn `cn` helper is the
one exception, and it is a file, not a directory.)

Promote shared code by **moving** it and updating the imports, never by copying.
`next-data-layout` carries the promotion triggers and the extract-don't-copy rule.

## One import alias

`@/*` maps to the repository root, and it is the only alias. Import shared code as
`@/lib/<domain>/<file>`.

A second alias over the same tree (`#/*`, a `package.json#imports` entry) is not a second
convenience, it is a second spelling: a grep for a module then finds half its callers, and the two
halves drift. A long relative chain (`../../../lib/...`) is the same problem in a different font.
Between neighbours in one directory, relative imports are fine.

## Where skills live: nest at project boundaries, not directory boundaries

A skill is offered to the agent standing in its directory, so nesting one is a claim that somebody
works _only_ there. Two kinds of "skill" can exist in this tree,
and they are unrelated: `.agents/skills/<name>/SKILL.md` at the root, for the coding agent working
on this project, and `mobile/.agents/skills/`, the mobile project's own.

- `.agents/skills/` at the root holds this project's skills, and `.claude/skills` is a symlink to
  it. A `SKILL.md` whose body opens with `<!-- Generated by dev-env -->` is generated — extend it
  with a sibling skill rather than editing it.
- **`mobile/` gets its own `.agents/skills/`**, plus `mobile/AGENTS.md`, `mobile/CLAUDE.md` and a
  `mobile/.claude/skills` symlink. It is a separate project, and an agent working inside it should
  not be handed this repository's database and web-framework skills. The root keeps only
  `mobile-boundary` — what the _root_ must do about the directory; everything about working inside
  it belongs down there.
- **No other directory gets them either.** `app/`, `lib/`, `prisma/`, `emails/`
  are directories of one project, and their skills are needed by _callers_ elsewhere — one nested
  there would not load where the decision is made.
