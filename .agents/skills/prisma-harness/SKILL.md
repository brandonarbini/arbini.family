## The canonical shape

```prisma
generator client {
  provider = "prisma-client"
  output   = "../generated/prisma"
}
```

`prisma-client`, not the legacy `prisma-client-js`. `output` names a **directory** at the repository
root, and Prisma emits `client.ts`, `browser.ts`, `enums.ts` and `models/` inside it — so imports are
`@/generated/prisma/client`, and an `output` of `"../generated/prisma/client"` nests everything one
level too deep. `@/*` must map to the repository root (`{ "@/*": ["./*"] }`); dev-env will not
rewrite a `src/`-aliased tsconfig to fit, because that would break the app's own imports.

`generated/` is gitignored, so a fresh checkout has no client until something generates one. That is
why `prisma generate` must be **first** in `postinstall` _and_ in `build`. The second is not
redundant: Vercel restores `node_modules` from the previous deployment's build cache, the install
then prints "Already up to date" and runs no lifecycle scripts at all, while the cache carries
`node_modules` and not a repo-root `generated/`.

## The pinned driver stack

`prisma`, `@prisma/client` and `@prisma/adapter-pg` share one tilde pin, and `pg` / `@types/pg` have
their own. Tilde rather than caret because the observed fleet drift happened _inside_ a caret range:
under an identical `^7.1.0` the fleet spread across 7.8 and 7.9 purely by install date, and Prisma
moves the generator and adapter shape within the major. The owned harness is written against one
shape of that stack, so a minor bump is a deliberate fleet-wide change here, not an install accident.

`overrides.pg` and `overrides["@types/pg"]` in `pnpm-workspace.yaml` are load-bearing for the same
reason and are easy to mistake for redundancy: `@prisma/adapter-pg` declares its own ranges, so
without the overrides the tree carries two copies. Types are nominal per copy, so the `PoolConfig`
the app builds stops being assignable to the one `PrismaPg`'s signature names — `new PrismaPg(config)`
fails to typecheck while every test still passes.

## Files the harness owns

Rewritten byte-for-byte on every apply — never edit them; report a wrong shape upstream to dev-env:

- `test/db.ts` — per-worker database provisioning, `migrationsHash()`, `truncateAllTables()`,
  `disconnectAppPrisma()`.
- `vitest.config.ts`, `vitest.env-setup.ts`, `vitest.global-setup.ts` — the template database, the
  per-worker clones, and the `DATABASE_URL` rewrite each worker gets.

Two files beside them are scaffolded once and then yours. `vitest.project.ts` is the project's half of
the config, merged into the owned one (arrays concatenate): an `exclude` for a directory whose tests
belong to another toolchain goes there, never into `vitest.config.ts`. `vitest.setup.ts` carries
app-specific module mocks. Two things in it are not yours to drop — `truncateAllTables` in an
`afterEach` and `disconnectAppPrisma` in an `afterAll`. Without them a suite leaks rows between tests
and leaves connections open at the end. `db-test-isolation` covers what that machinery makes true for
the tests themselves; do not write cleanup code of your own.

Nothing shells out to set the database up any more: `vitest.global-setup.ts` builds the template
database and each worker clones it. The retired simple tier's `.devcontainer/test-database.sh` is
removed on the next dev-env apply, and the `pretest`, `pretest:run` and `test:db:*` scripts that
invoked it have to go with it — left in `package.json` they initialize, reset or migrate an obsolete
shared database before every run.

`test:env` wraps every test entry point with `dotenv-cli` so `.env.test` wins over `.env` (`-o`),
which is what points the suite at the test database rather than the development one. Its
`DATABASE_URL` carries `connection_limit=1`, keeping each Vitest worker's pool to a single connection
so `availableParallelism()` workers cannot exhaust PostgreSQL, and the database name is derived so
per-worker clones stay inside PostgreSQL's 63-byte identifier limit.

## Two files dev-env will not write

Both break _after_ a clean apply rather than during it:

- **`prisma/migrations/`.** `migrationsHash()` reads that directory before every suite, so a missing
  one is an ENOENT crash rather than an empty hash. Bootstrap it offline, no database needed:
  `prisma migrate diff --from-empty --to-schema prisma/schema.prisma --script -o prisma/migrations/<timestamp>_init/migration.sql`,
  plus a `migration_lock.toml` containing `provider = "postgresql"`.
- **A committed `.env`.** `prisma.config.ts` reads `DATABASE_URL` from it, `test:env` loads it, and
  the Cursor bootstrap rewrites its datasource host. Use database `postgres` — Compose sets
  `POSTGRES_DB: postgres` and nothing provisions a per-project development database, so any other
  name fails P1003. The placeholder in `.env.example` is a shape, not a database that exists.

## Schema conventions

These hold across every managed schema, so a model that departs from them is the odd one out for
the next reader:

- **Ids are database-generated UUIDs**:
  `String @id @default(dbgenerated("gen_random_uuid()")) @db.Uuid`, with `@db.Uuid` on every
  foreign key that points at one. Never `cuid()` or `uuid()`. Copying the nearest neighbour is
  only safe once the whole schema agrees, which is why the leftover is a finding.
- **Money is `Int` cents.** Never a float, never `Decimal`, never a formatted string. Dollars are
  produced in exactly one formatting function so rounding and currency have a single definition.
- **Mirrored data is soft-deleted.** A table that mirrors an upstream system of record sets
  `deleted_at` and nothing removes rows; its foreign keys are `Restrict`, so an accidental delete
  fails loudly instead of cascading through the mirror.
- **A rename is hand-written.** `migrate dev` renders one as `DROP` + `CREATE`; load
  `prisma-rename-migrations` before renaming anything the database already holds.

## Everyday commands

Run each inside the devcontainer (`devcontainer exec --workspace-folder . <command>`):

- Create a migration from an edited schema: `pnpm exec prisma migrate dev --name <name>`. No script
  does this — every script below only applies migrations that already exist, so reaching for one of
  them after a schema edit leaves the edit unmigrated.
- Apply the migrations that exist to a fresh or stale database: `pnpm prisma:initialize`.
- Seed development data: `pnpm db:seed`.

Edit the schema, generate a migration, commit the migration directory with the schema change.
`migrate dev` only ever writes a new migration: it will not rewrite or rename an existing one, and
pointing it at a migration already applied elsewhere resets the database rather than editing it in
place. Never hand-edit a migration that has been applied anywhere, and never edit anything under
`generated/`.
