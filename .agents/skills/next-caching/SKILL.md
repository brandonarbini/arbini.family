Companion skills: `next-data-layout` (the two-layer structure `cacheTag`s live inside)
and `next-server-actions` (where `updateTag()` is called after a mutation).

## Prerequisite: Cache Components

Everything below assumes **Next.js 16+ with Cache Components enabled**
(`cacheComponents: true`, top-level in `next.config.ts`), which provides the stable
`'use cache'`, `cacheTag`, `cacheLife`, and `updateTag` APIs. If it isn't enabled, don't
silently enable it project-wide: in an interactive run, ask; in a non-interactive run,
write the structure cache-free and leave a `TODO` where `'use cache'`/tags would go.
Projects on the older model use `unstable_cache`, which this skill does not cover.

## Cache directives live inside `data.ts`

Rule 11: put `"use cache"` at the top of each query, with `cacheTag()` and optionally
`cacheLife()`. Arguments automatically become the cache key. Callers never see these
primitives. Not: manually constructing key arrays; not: `unstable_cache` in a Cache
Components project (use `'use cache'`); not: wrapping a `'use cache'` query in
`React.cache()` (redundant) — but for an intentionally-uncached `data.ts` read,
`React.cache()` **is** the correct per-render dedup tool.

## Tags are exported constants

Rule 4: cache tags are exported constants, never string literals. A tag used only inside
one route can live in that route's `./data.ts`; the moment anything outside touches it
(sibling `actions.ts`, webhook, cron), move it to `/lib/<domain>/cache.ts` — see
`next-data-layout`. Mutations import the constant and pass it to invalidation, below.

The one load-bearing shape — a tag builder, never a raw string:

```ts
export const DISCOUNT_TAGS = {
  discountCodes: (organizationId: string) => `discount-codes:${organizationId}`,
  discountCode: (id: string) => `discount-code:${id}`,
} as const;
```

## Invalidation (Rule 10, the caching half)

After a Server Action mutates, call `updateTag()` for read-your-own-writes invalidation —
it works **only** inside Server Actions (the mutation half of this rule, and what else
belongs in `actions.ts`, is `next-server-actions` Rule 10). Webhooks, cron jobs, and other
Route Handlers can't call `updateTag()`; they use `revalidateTag(tag, 'max')` for
stale-while-revalidate, or `revalidateTag(tag, { expire: 0 })` for immediate expiration —
the one-argument `revalidateTag(tag)` is deprecated. Use `revalidatePath()` only when no
tag covers the change.

External callers — webhooks, cron jobs, integrations — import the same tag constants from
`/lib/<domain>/cache.ts` and call `revalidateTag`, never `updateTag`:

```ts
// app/api/webhooks/discount-redemption/route.ts — full version in
// next-data-layout's references/templates.md
revalidateTag(DISCOUNT_TAGS.discountCode(event.discountCodeId), "max");
revalidateTag(DISCOUNT_TAGS.discountRedemptions(event.discountCodeId), "max");
```

`'max'` gives stale-while-revalidate semantics — current users see cached data while
fresh data loads in the background. Pass `{ expire: 0 }` instead if the external system
requires immediate expiration.

## `loading.tsx` / Suspense (Rule 12)

A page that awaits runtime data requires `loading.tsx` or a parent `<Suspense>`. Under
Cache Components, any page that awaits `searchParams`, calls cookie-reading auth, or
awaits an uncached query accesses uncached data during render; without a sibling
`loading.tsx` or parent Suspense boundary, `next build` fails with the blocking-route
error ("Uncached data was accessed outside of `<Suspense>`"). Streaming is the bonus, not
the reason. Independent queries on one page start in parallel (`Promise.all` or
Suspense-per-section) — sequential awaits waterfall.

## Rationale

- **Why `data.ts` is pure** — it's framework-enforced, not just style: a `'use cache'`
  function that calls `cookies()`/`headers()` or other runtime APIs errors immediately
  (`next-request-in-use-cache`). Keeping auth at entry points also makes queries testable
  and reusable in scripts/jobs. (`'use cache: private'` is the documented escape hatch,
  but it's out of this pattern.)
